# Phase 2 — Live adapter, recordings, caps, real eval

**Status: draft for Shane's review (written at the Phase 1 gate, 2026-10-19). Nothing here is started.** Phase 2 is the first phase that spends money. It adds one runtime dependency, calls the Claude API under hard caps, records the responses once, and from then on every test replays the recordings. Source for the API facts below: the decisions they cite (D-17..D-19, O-1..O-10), which record the docs as read on 2026-10-19; each live-API fact is re-read from the docs when its task starts, and a difference is a decision entry before it is code.

Exit bar: one recorded run per fixture batch committed under `recordings/`; `triage:eval --provider recorded` prints the brief §11 report from them beside the scripted one; cost and cache-read share measured from usage fields; T re-chosen on the dev split and reported once on test; Shane's 30 hand judgements recorded; `docs/EVAL.md` shows scripted and recorded side by side. CI still holds no secret and spends nothing.

## Decisions to make before 2.1 (Shane)

- **Q1 Spend.** Approve `@anthropic-ai/sdk` as the one runtime dependency, an API key in `.env` on the Mac only, and the caps at their defaults (`TRIAGE_RUN_CAP_CENTS` 200, `TRIAGE_PROJECT_CAP_CENTS` 1500; O-2). The scripted estimate for recording both batches is under 1 dollar at batch prices (O-2), but that estimate is made from the scripted token counts, which are estimates.
- **Q2 Recordings layout.** Phase 1 left two layouts open: `triage:run --provider recorded` reads `<dir>/tier{A,B}.jsonl` (the PRD's `recordings/<run>/`), while the oracle and `triage:eval --provider recorded` look for `fixtures/recorded_tier{A,B}_batch{N}.jsonl`. Proposed: `recordings/<batch>/tier{A,B}.jsonl`, with the eval and the oracle both pointed there (a change to `reference_pipeline.py`, so a decision entry first).
- **Q3 Audit seed.** The D-21 sample is seeded by `--audit-seed`, default 20261019, recorded on each ledger row, because the policy file carries the share but not the seed. Keep, or move the seed into a `policy.v2.json` (which changes the D-26 hash and needs a fresh EVAL.md).
- **Q4 Where the live run happens.** The live provider needs the key, so 2.5 runs on the Mac (or a session with the key), never in CI or a cloud session without it.

## Tasks

- [ ] **2.1 SDK and decision.** Add `@anthropic-ai/sdk` with a decision entry (version, why, what it may touch). Only `src/providers/live.ts` imports it; `policy:lint` already forbids `anthropic` under `src/pipeline/`. *Acceptance:* `npm ci` clean; lint fails if `src/pipeline/` imports the SDK; no test imports `live.ts`.
- [ ] **2.2 Live provider.** One Message Batch per (tier, run) (D-17): `custom_id` = ticket id; system prompt + output schema as the cached prefix with `cache_control` `{type: ephemeral, ttl: "1h"}` on the system block; structured output through `output_config.format` `{type: json_schema, schema}`; the prefix bytes asserted identical across every request in the batch before submit; poll; stream results; write each line to `recordings/<run>/tier{A,B}.jsonl` unchanged as it arrives. Refuses unless `TRIAGE_LIVE=1` and a key (already in `getProvider`). *Acceptance:* a `*.live.test.ts` (excluded from vitest and CI) submits 2 tickets; a unit test with a fake client checks the request body, the prefix assertion and that a changed prefix byte throws.
- [ ] **2.3 Projection and caps (D-19).** Before submit: estimated tokens × price with the cache assumed to miss, refuse over `TRIAGE_RUN_CAP_CENTS` or if the ledger plus the projection passes `TRIAGE_PROJECT_CAP_CENTS`. After results: real cost from usage fields; over the run cap marks the row `OVER_CAP` and latches further live runs off until `--acknowledge-over-cap`. No flag removes a cap. *Acceptance:* tests on fake usage cover refuse-before, over-after, the latch and the project cap; the estimate is labelled "estimate" wherever printed.
- [ ] **2.4 Model id check.** `models.list()` before the first live submit; a tier model the API does not list, or a model with no price row, refuses (O-1). *Acceptance:* fake-client tests for both refusals.
- [ ] **2.5 Record.** One live run per fixture batch on the default pair, under the caps, on the Mac. Commit `recordings/` and the ledger rows' numbers (the ledger itself stays in `data/`). Latency fields filled (O-10): `submitted_at`, `completed_at`, p50/p95 in integer seconds. *Acceptance:* both runs `cap_status ok`; recordings read by `src/io/results.ts` with 0 errors; real spend stated in cents.
- [ ] **2.6 Recorded eval.** `triage:eval --provider recorded` prints the same report from the recordings; the per-ticket diff against the scripted reference decisions is off for recorded results (they will differ, which is the point), and the oracle reproduces the recorded report so the two still agree. Print the cache-read share of tier-A input tokens. *Acceptance:* TypeScript and oracle outputs equal on the recordings; CI replays the recordings with no key.
- [ ] **2.7 Threshold on real results (D-16, O-3).** Sweep T on batch 1's dev split from the recordings; choose T; report it once on the test split. A changed T is a policy v2 with a fresh EVAL.md. *Acceptance:* the sweep and the test line in EVAL.md.
- [ ] **2.8 Shane's 30 (D-24).** Shane reads 30 human-queue tickets from the recorded run and records, per ticket, whether a person needed to see it and why, in `eval/labels/shane-30.json`; the eval prints agreement with the pipeline's reasons and the share he would have auto-handled. Then O-3 and the needs_human rules are re-decided. *Acceptance:* the file, the printed agreement, and the decision entries.
- [ ] **2.9 EVAL.md.** Scripted and recorded side by side, each with its results source, fixture and recording hashes, policy hashes, real cost and cache-read share, and the D-23 wording.

**Not in Phase 2:** the synchronous `messages` provider for N9 (Phase 3, O-10), the HTTP handler, ledger views, reviewer agreement, a third tier.
